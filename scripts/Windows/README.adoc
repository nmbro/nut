NUT and MS Windows
==================

Introduction
------------

NUT is also available for the Microsoft Windows platform, built with the
link:https://www.mingw-w64.org[MinGW-w64] toolchains (GCC and the Windows
headers and C runtime libraries), either semi-natively on Windows in the
link:https://www.msys2.org/[MSYS2] environments, or cross-compiled on Linux.

This methodology (and Windows support in general) are still experimental, so
pull requests are welcome to tie up some loose ends (test and fix programs,
re-enable some code commented away by `#ifdef` directives...)

The Windows versions which NUT sources aim to support, which ones a
particular build runs on (depending on its C runtime), and how to deliver
the Universal C Runtime with a bundle for Windows 7 SP1, 8 and 8.1, are
detailed in linkdoc:qa-guide[Prerequisites for building NUT on different
OSes,NUT_Config_Prereqs,docs/config-prereqs.txt] (see "Windows builds").

Choosing a build environment
----------------------------

MSYS2 offers several environments, which differ by the target architecture
and C runtime (and so by the Windows versions the results run on) and by the
set of packages they offer:

[options="header"]
|===============================================================================
| Environment | Bits | C runtime | Notes
| UCRT64      | 64   | UCRT      | Recommended for 64-bit builds, used by the
                                   AppVeyor CI. Packages nearly all NUT
                                   dependencies. Results need Windows 10 or
                                   newer, or the UCRT (see above).
| MINGW32     | 32   | MSVCRT    | For 32-bit builds, used by the GHA-09 CI
                                   workflow. Offers the toolchain but few
                                   packages; the other dependencies are built
                                   from sources (see below). Results run on
                                   Windows 7 SP1 and newer.
| MINGW64     | 64   | MSVCRT    | No longer offers `libusb` (1.0) nor `neon`
                                   packages, so NUT built there would lack USB
                                   and XML drivers.
| CLANG64     | 64   | UCRT      | Clang instead of GCC; not regularly tested.
|===============================================================================

There is no 32-bit UCRT environment in MSYS2.

The MSYS2 environment is selected by the shortcut used to start its terminal
(e.g. "MSYS2 UCRT64"), or by setting `MSYSTEM` (e.g. `MSYSTEM=MINGW32`) for a
login shell (`bash -l`), which then sets `MINGW_PREFIX` (e.g. `/ucrt64`),
`MINGW_PACKAGE_PREFIX` (e.g. `mingw-w64-ucrt-x86_64`), `MINGW_CHOST` and the
`PATH` accordingly. To avoid mixing toolkits of different environments, keep
`${MINGW_PREFIX}/bin` early in the `PATH`.

Building in MSYS2
-----------------

Installing MSYS2, updating it, and enabling symbolic links (which NUT build
recipes and scripts use) are described in linkdoc:qa-guide[Prerequisites for
building NUT on different OSes,NUT_Config_Prereqs,docs/config-prereqs.txt]
(see "Windows with MSYS2").

MSYS2 packages
~~~~~~~~~~~~~~

The CI builds (see `.github/scripts/appveyor/02-install.bat`) install these
packages, with `${MINGW_PACKAGE_PREFIX}` of the current environment, skipping
those which it does not package (`pacman -Sp` tells):

----
:; for P in base-devel \
    ${MINGW_PACKAGE_PREFIX}-binutils ${MINGW_PACKAGE_PREFIX}-crt \
    ${MINGW_PACKAGE_PREFIX}-gcc ${MINGW_PACKAGE_PREFIX}-headers \
    ${MINGW_PACKAGE_PREFIX}-libgomp ${MINGW_PACKAGE_PREFIX}-libstdc++ \
    ${MINGW_PACKAGE_PREFIX}-libwinpthread ${MINGW_PACKAGE_PREFIX}-make \
    ${MINGW_PACKAGE_PREFIX}-pkgconf ${MINGW_PACKAGE_PREFIX}-winpthreads \
    autoconf-wrapper automake-wrapper libtool ${MINGW_PACKAGE_PREFIX}-libltdl \
    ${MINGW_PACKAGE_PREFIX}-ccache git aspell aspell-en python \
    ${MINGW_PACKAGE_PREFIX}-libusb ${MINGW_PACKAGE_PREFIX}-libsystre \
    ${MINGW_PACKAGE_PREFIX}-neon ${MINGW_PACKAGE_PREFIX}-libpng \
    ${MINGW_PACKAGE_PREFIX}-cppunit ${MINGW_PACKAGE_PREFIX}-nss \
    ${MINGW_PACKAGE_PREFIX}-sqlite3 ${MINGW_PACKAGE_PREFIX}-zlib \
    nsinstall zip ${MINGW_PACKAGE_PREFIX}-openssl \
  ; do if pacman -Sp $P >/dev/null 2>&1 ; then LIST="$LIST $P" ; \
    else echo "SKIP: $P" ; fi ; done ; pacman -S --needed $LIST
----

Notes:

* `libsystre` provides the POSIX `regex.h` API (it wraps the TRE library),
  which NUT and `net-snmp` need.
* `sqlite3`, `zlib`, `nsinstall` and `zip` are needed to build NSS from
  sources where it is not packaged (e.g. MINGW32), and `libpng` and `zlib`
  for `libgd`.
* The MSYS (not MinGW) `python` is enough for the NUT test suite (PyNUT);
  documentation builds (`asciidoc`, `a2x`) are not covered here, the CI
  builds go without them (`--with-docs=no`).
* `libgd` is deliberately not installed from MSYS2: its package enables all
  image formats, so about 30 more DLLs (e.g. video codecs for its HEIF and
  AVIF support) would have to be delivered with NUT; a PNG-only one is
  built from sources instead (see below).
* Neither `net-snmp` nor `libmodbus` with USB (RTU over USB) support are
  packaged; they are built from sources for all environments.
* A download mirror may refuse requests for a while (e.g. HTTP 429 Too Many
  Requests); then run `pacman -S` again: what was downloaded stays in the
  pacman cache.

Prerequisites built from sources
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

The `build-mingw-prereqs.sh` script in this directory builds the dependencies
which the current environment does not package (as `pkg-config` tells), and
installs them into its prefix. Run it in the MSYS2 terminal of the wanted
environment, with `MSYS2_PATH` set (otherwise it assumes a Linux cross-build,
see below):

----
:; export MSYS2_PATH=1
:; ./scripts/Windows/build-mingw-prereqs.sh
----

It downloads (and verifies the checksums of) the sources into `DLDIR`
(default: `~/nut-win-deps`) and builds them in a subdirectory per `ARCH`,
where it also keeps an installation tree of each, so that later runs (e.g.
in a new MSYS2 installation with a restored `DLDIR`) only re-install them.
Pass `-f` to rebuild everything anyway. `NUT_PREREQS_ONLY` can limit it to
some of the `provide_*()` steps, e.g. `NUT_PREREQS_ONLY="libregex libusb"`.

[options="header"]
|===============================================================================
| Dependency        | Built where not packaged, e.g.  | Notes
| regex (TRE and the MSYS2 "systre" wrapper) | Linux cross-builds | Also
  installed as `libregex` and `libgnurx`, like the MSYS2 `libsystre` package.
| `libusb` (1.0)    | MINGW32, MINGW64, Linux cross-builds |
| `libltdl`         | Linux cross-builds | For `nut-scanner` (which loads the
  libraries of the scanned protocols at run time).
| `cppunit`         | MINGW32, Linux cross-builds | Only for the C++ client
  library tests (`make check`).
| NSPR and NSS      | MINGW32, Linux cross-builds | Same versions and patches
  as the MSYS2 packages for the 64-bit environments.
| OpenSSL, `expat`  | Linux cross-builds | For `neon` (and OpenSSL for NUT).
| `neon`            | MINGW32, MINGW64, Linux cross-builds | With OpenSSL and
  expat, without NLS.
| `libpng`          | Linux cross-builds | For `libgd`.
| `libgd`           | all | A minimal (PNG only) build for `upsimage.cgi`.
| `net-snmp`        | all | For `snmp-ups` and the SNMP scan of `nut-scanner`.
| `libmodbus`       | all | NUT's fork with USB (RTU over USB) support, rebuilt
  when its Git source changes.
|===============================================================================

For security libraries in particular, keep these up to date: where MSYS2
packages a newer version (for UCRT64) of a dependency than the script
builds, it prints a warning (on GitHub Actions also an annotation and a job
summary line), so that its `DEP_VERSION`, checksum and MSYS2 recipe commit
can be updated.

NOTE: The `ccache` 4.14 of MINGW32 requires the `USERPROFILE` and
`LOCALAPPDATA` environment variables, which a login shell started from
another program (e.g. CI or IDE) may lack; otherwise compilers fail with
"The USERPROFILE environment variable must be set" messages, which make
`configure` scripts conclude that the "C compiler cannot create executables".

Building NUT
~~~~~~~~~~~~

The `ci_build.sh` script in the NUT source root handles MSYS2 builds (with
`ccache` if installed). The CI builds use (see
`.github/scripts/appveyor/04-build_script.bat`):

----
:; CI_SKIP_CHECK=true CANBUILD_WITH_LIBMODBUS_USB=yes \
   WITH_LIBNUTPRIVATE=true NUT_SSL_VARIANTS=nss \
   ./ci_build.sh --with-docs=no
----

* `NUT_SSL_VARIANTS=nss` builds with NSS for SSL/TLS (as the CI bundles
  are); `openssl` is possible too.
* `WITH_LIBNUTPRIVATE=true` builds the NUT common code as a shared private
  library, which the programs of the bundle share, instead of linking it
  into each one.
* With `DO_USE_AUTOCONF_CACHE=yes` and `CI_CACHE_NUT_BASEDIR` set, the
  `configure` results are kept (`config.cache` files) for later builds with
  the same `configure.ac`, `m4/*.m4`, options and environment; `configure`
  takes several minutes in MSYS2.

Alternatively, use the usual `./autogen.sh && ./configure && make` steps.

Testing
~~~~~~~

`make check` (`.github/scripts/appveyor/07-test_script.bat` runs it like the
CI builds do) runs the unit tests, the C++ client library tests (with
`cppunit`), and the NUT Integration Testing suite (NIT: data server, dummy
drivers, clients including PyNUT, with SSL/TLS), which needs a `NUT_STATEPATH`
directory for its state files, as a Windows path:

----
:; export NUT_STATEPATH='C:\Users\me\AppData\Local\Temp\nut-test'
:; mkdir -p "$NUT_STATEPATH"
:; make -j 2 check
----

Bundling NUT for Windows
~~~~~~~~~~~~~~~~~~~~~~~~

`make install-win-bundle DESTDIR=...` installs NUT into the `DESTDIR` and
adds the DLLs (from the MSYS2 environment) which the NUT programs and
libraries need, so that the bundle runs on a Windows system without MSYS2.
The CI builds pack such a bundle as an archive
(`.github/scripts/appveyor/08-after_test.bat`). Options (as `make` or
environment variables):

* `WIN_BUNDLE_DEVEL=yes` keeps the files only needed to build programs
  against NUT (headers, static and import libraries, `pkg-config` files),
  and NUT libraries which no bundled program uses (e.g. the C++
  `libnutclient`); by default they are removed, as is the PyNUT module
  (published on PyPI as "PyNUTClient").
* `WIN_BUNDLE_STRIP=no` keeps the debug information in NUT programs and
  libraries; by default it is removed (about halving the bundle size).
* `WIN_BUNDLE_DEBUGINFO_DIR=...` saves that debug information first, as
  `<path in bundle>.debug` files with `.gnu_debuglink` references from the
  stripped files, e.g. to deliver it separately for crash analysis (as the
  CI builds do).
* `WIN_BUNDLE_UCRT_DIR=...` (a `Redist/ucrt/DLLs/<arch>` directory of a
  Windows SDK, or `auto` to look for an installed SDK) delivers the UCRT
  DLLs "app-locally" with a UCRT-based build, so that it can start on
  Windows 7 SP1, 8 and 8.1 without the UCRT update.

The `nutconf` program is the only C++ program in the bundle; with a private
`libnutconf` it is linked with static GCC runtime libraries, so the bundle
does not carry `libstdc++-6.dll` for it alone.

To see which DLLs a program needs, e.g. when checking a bundle for another
Windows version, `dllldd.sh` in this directory lists them (also used by the
bundle recipes), as does `objdump -p FILE | grep 'DLL Name'`.

Cross-building on Linux
-----------------------

NUT for Windows can also be cross-compiled on Linux, e.g. on Debian or Ubuntu
(also in WSL2, or in containers), with the MinGW-w64 toolchains:

----
# MSVCRT toolchains (like MSYS2 MINGW32 and MINGW64):
:; sudo apt-get install mingw-w64
# UCRT toolchain (like MSYS2 UCRT64), packaged by Debian 13 and newer
# (not by Ubuntu 24.04), named x86_64-w64-mingw32ucrt:
:; sudo apt-get install gcc-mingw-w64-ucrt64 g++-mingw-w64-ucrt64
----

Besides the NUT build prerequisites (`autoconf`, `automake`, `libtool`,
`pkgconf`, `make`, `python3`, `perl`, `curl`, `patch`, `xz-utils`, `dpkg-dev`... as
detailed in linkdoc:qa-guide[Prerequisites for building NUT on different
OSes,NUT_Config_Prereqs,docs/config-prereqs.txt]), Debian packages
`libz-mingw-w64-dev` (zlib, for the MSVCRT toolchains and, on Debian 13,
also for the UCRT one), but no MinGW builds of the other NUT dependencies;
`build-mingw-prereqs.sh` builds them when run without `MSYS2_PATH`. Its
environment variables:

* `ARCH`: the host triplet, e.g. `x86_64-w64-mingw32` (default) or
  `i686-w64-mingw32`;
* `PREFIX`: where to install the dependencies, default `/usr/$ARCH` (where
  the toolchain itself is, so `sudo` is used for that unless `SUDO=" "`);
* `HOST_FLAG` (default `--host=$ARCH`) and `BUILD_FLAG` (by default
  `--build=` the `dpkg-architecture -qDEB_BUILD_GNU_TYPE` value). These
  defaults only apply when `PREFIX` is not set: with a custom `PREFIX`, set
  them too, or the dependencies get built with the native compiler;
* `CC`, `CXX`, `AR`, `RANLIB` and the resource compiler (`RC` for libtool,
  `WINDRES` and `WINDMC` for NUT) if the tool names differ from the
  `ARCH`, e.g. for the UCRT toolchain (with `ARCH=x86_64-w64-mingw32` for
  the `configure` scripts, as older `config.sub` copies do not know the
  `x86_64-w64-mingw32ucrt` name). As `configure` scripts look for more
  tools by the host triplet (e.g. `dlltool`), it is simpler to offer the
  UCRT tools under the `x86_64-w64-mingw32-*` names too, e.g. as symbolic
  links in `/usr/local/bin` on a system without the MSVCRT toolchain (as
  the CodeQL job does):
+
----
:; for T in /usr/bin/x86_64-w64-mingw32ucrt-* ; do \
     sudo ln -s "$T" "/usr/local/bin/x86_64-w64-mingw32-${T#/usr/bin/x86_64-w64-mingw32ucrt-}" ; \
   done
----
* `DLDIR` and `NUT_PREREQS_ONLY`, as above;
* `MAKEFLAGS`, e.g. `MAKEFLAGS=-j16` (default `-j 8`).

For example, as the CodeQL analysis of the Windows code does (see
`.github/workflows/05-codeql.yml`, which runs this as root in a Debian
container):

----
:; TOOLCHAIN=x86_64-w64-mingw32ucrt
:; HOST_FLAG="--host=x86_64-w64-mingw32" \
   BUILD_FLAG="--build=`dpkg-architecture -qDEB_BUILD_GNU_TYPE`" \
   ARCH=x86_64-w64-mingw32 PREFIX="/usr/$TOOLCHAIN" \
   CC="$TOOLCHAIN-gcc" CXX="$TOOLCHAIN-g++" \
   AR="$TOOLCHAIN-ar" RANLIB="$TOOLCHAIN-ranlib" \
   RC="$TOOLCHAIN-windres" WINDRES="$TOOLCHAIN-windres" \
   NUT_PREREQS_ONLY="libregex libusb libltdl" \
   ./scripts/Windows/build-mingw-prereqs.sh
----

The state of the `provide_*()` steps in cross-builds (most were developed
for MSYS2):

[options="header"]
|===============================================================================
| Step              | In cross-builds
| `libregex`, `libusb`, `libltdl` | Built (32-bit and 64-bit, MSVCRT and
  UCRT); exercised by the CodeQL CI job.
| `cppunit`         | Built in a manual test (MSVCRT).
| `nspr`            | Its build-time tools need a native compiler (`HOST_CC`,
  `gcc` by default in cross-builds); not tested yet.
| `nss`             | Its own `make` system gets the cross tool names, a
  natively built `nsinstall`, and `CROSS_COMPILE=1` (no library signing),
  and uses the `sqlite3` copy which NSS bundles; not tested yet.
| `openssl`, `expat`, `libpng` | Built only in cross-builds (MSYS2 packages
  them), for `neon` (OpenSSL and `expat`), `libgd` (`libpng`) and NUT
  itself (OpenSSL, as an alternative to NSS); not tested yet.
| `neon`, `libgd`   | Need the above; not tested yet.
| `netsnmp`, `libmodbus_git` | Not tested yet (they now get the cross-build
  flags; `net-snmp` also needs the regex library).
|===============================================================================

Without the untested ones, cross-built NUT has no SSL, XML, CGI, SNMP or
Modbus support; with `libltdl` it does have `nut-scanner` (for the protocols
available). Reports and fixes are welcome. Note that by default (without
`NUT_PREREQS_ONLY`) the script tries all of them, and fails at the end if
any is missing. OpenSSL is configured with its own `Configure` script (which
needs `perl`): in cross-builds it gets `--cross-compile-prefix=$ARCH-`,
unless `CC` (and `AR`, `RANLIB`, `RC`) name the tools, e.g. for UCRT.

To build NUT itself, the `build-mingw-nut.sh` script in this directory sets
the cross-build flags (for `/usr/$ARCH` prefixes, or `/usr/$TOOLCHAIN` if
set, e.g. `TOOLCHAIN=x86_64-w64-mingw32ucrt` for a UCRT build with `all64`),
runs `configure` and `make`, and installs the result with the DLLs it needs
(by `make install-win-bundle`, see above; or with its own older logic, if
`INSTALL_WIN_BUNDLE=false`) into `nut_install_${ARCH}` (with a `nut_install`
symbolic link to the latest one). Pass e.g. `MAKEFLAGS=-j16` for parallel
builds.

* out-of-tree from the Git source (default):

	:; (cd scripts/Windows/ && ./build-mingw-nut.sh all64)
	:; (cd scripts/Windows/ && ./build-mingw-nut.sh all32)
	:; (cd scripts/Windows/ && TOOLCHAIN=x86_64-w64-mingw32ucrt ./build-mingw-nut.sh all64)

* from a NUT release tarball (`SOURCEMODE=stable`, optionally with
  `VER_OPT`), or from a `make dist` tarball of the current sources
  (`SOURCEMODE=dist`).

The NUT CI script calls it too (with parallel `make`):

----
:; BUILD_TYPE=cross-windows-mingw-32 ./ci_build.sh
:; BUILD_TYPE=cross-windows-mingw-64 ./ci_build.sh
----

To check that a cross-built bundle starts, e.g. that it has all the DLLs
it needs, its programs can be run with Wine (e.g. `wine bin/upsc.exe -V`):
a missing DLL is reported as "Library ... not found".

Notes for 32-bit builds
-----------------------

* Methods of the Windows API, and of some libraries (e.g. `libgd`), use the
  calling convention of the Windows API in 32-bit builds, where it differs
  from the C one (in 64-bit builds they are the same). Their names are then decorated with the size
  of their arguments (e.g. `gdImagePng@8`), so link checks which declare
  such methods themselves (like `AC_SEARCH_LIBS()`) fail: the NUT `configure`
  checks for `libgd` include its header instead. Callbacks passed to such
  libraries must be declared with the same convention, e.g. `LIBUSB_CALL`
  for `libusb` hotplug and transfer callbacks, or programs crash.
* `size_t` and `long` are 32 bits, and so is `time_t` in MINGW32: use the
  NUT format macros (e.g. `PRIuSIZE`) rather than hard-coded `%ll...` ones.

Continuous integration
----------------------

* AppVeyor (`appveyor.yml`) builds, tests and bundles NUT for Windows in the
  MSYS2 UCRT64 environment, with the step scripts in
  `.github/scripts/appveyor/`. Pull request builds restore the build cache
  but do not save it.
* The GitHub Actions workflow "GHA-09" (`.github/workflows/09-windows-mingw32.yml`)
  does the same in the MSYS2 MINGW32 environment (32-bit), calling the same
  step scripts with `NUT_MSYSTEM=MINGW32` (also `NUT_SSL_VARIANTS`,
  `NUT_BUNDLE_ARCH`, `NUT_BUNDLE_VERSION` and `NUT_STATEPATH` select other
  settings than the AppVeyor defaults). Its caches of MSYS2 packages,
  prerequisites built from sources, `ccache` and `configure` results are
  saved by `master` branch builds; its job summary reports how long each
  step took, how the caches were restored and the archive sizes.
* The CodeQL workflow "GHA-05" also analyzes the Windows-specific code,
  with cross-builds for 32-bit (MSVCRT) and 64-bit (UCRT) Windows.
